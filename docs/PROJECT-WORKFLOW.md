# Life Skills: one maintained project state

This implements the owner's 11 September request to clarify rambles, save decisions and complete work economically. It extends the existing registered Operating Protocol; it does not introduce another control workbook, SDK or business master. Current task-specific authorization remains valid.

## Authority by domain

| Question | Authority | Evidence of completion |
| --- | --- | --- |
| What does the owner want? | Latest explicit owner decision, reconciled into the registered CURRENT Product/Website/Program source | Same-file revision and readback linked to one change ID |
| Which design, words or photo? | `creative/**` logical registry and approved image bytes; private original/provider bindings resolved from registered handoff | Actual file, checksum, scope and hash-bound owner evidence |
| What is being worked on? | Existing Build Control during preparation; Git issues/PRs for admitted engineering lanes | Current owner/lease, dependencies, exact branch/head and next action |

| What was generated or posted? | Provider job/output/delivery receipt plus canonical asset/job state | Saved bytes, QA result and distinct published/scheduled status |

Source-repository changes do not automatically reach the BNA production repository. A Drive revision does not automatically change a running Codex session. Every worker starts/resumes from current source fingerprints, accepted commit pointers and its own scope.

## Ramble to saved decision

1. Capture the relevant owner instruction in its existing private work record. Distill facts, explicit corrections, proposals, implementation tasks and unresolved questions. Do not expose a private raw transcript in this public repo.
2. Read the current targeted source first. Identify what already exists and what was already approved. Do not ask the owner to reattach a registered file or approve the same choice again.
3. Use judgment to develop the idea: point out a meaningful tradeoff or missing constraint, resolve what the evidence answers, and ask one focused question when the remaining answer materially changes the outcome. A precise correction such as “Self-governance” is directly actionable.
4. Produce a bounded before/after change against the canonical state. Resolve vague placement words into exact affected bounds/deltas for one candidate; do not pass “slightly higher” as an executable specification.
5. Apply authorized changes to the existing source and its dependent contracts. Record one change ID in the existing Change Log with old/new revisions, affected work, verification and unresolved steps. Read back before calling it saved.
6. Execute in the appropriate lane. A master-image change belongs to the image-producing worker; code consumes the approved pixels. A website control change belongs to Codex. A brainstorm does not automatically authorize paid generation, posting or deployment; apply the user's actual standing/task authorization.

## Reliable propagation, without an approval maze

Drive and Git are separate systems; do not claim an atomic transaction across them. Under one change ID, track which source edits, private bindings, derived manifests, tasks and accepted-commit pointers have been applied. An interrupted change resumes from the recorded step; it does not create another “FINAL” document.

Use expected versions/hashes before writes. Preserve another worker's active claim and unrelated fields. Invalidate only dependent jobs/receipts when a source changes. Preserve completed work; a stale manifest is not a reason to regenerate an image. The latest explicit owner correction wins over old snapshots, but workers must not silently choose between genuinely unresolved business decisions.

Coordination is the existing lane-appropriate protocol. The old embedded Work Graph read/write/read claim instructions are stale where the current Operating Protocol requires append-only Control Events and a winning fence. Do not invent a new lock table or assume a cooperative lease grants protected Git/provider access.

## Keep recurring work inexpensive

- Parse an already structured request and compare file/source hashes with ordinary code. Healthy checks, index updates, source resolution and known-asset reuse do not need a language-model call.
- Cache verified sources by revision/hash and revalidate within the current preparation/publication freshness requirements. Fetch changed content when needed; caching never substitutes for a required fresh source receipt.
- Use AI for ambiguous intent, substantive copy, visual judgment or a real code problem. Meter optional intent-model calls separately from image credits and advertising spend.
- Deduplicate image jobs by exact master/photo/copy/settings. Save the provider history ID before waiting. Resume an uncertain job rather than paying to recreate it.
- Batch only after the relevant visual master is approved. Within the authorized budget, proceed through the approved queue without repeatedly asking permission. New art direction gets one candidate first.

## What may repair itself

Automatically rebuild derived indexes, retry a safe read/download, refresh a task projection from canonical records, and finish an interrupted known change when its versions/authorization still match. Record what was repaired.

Escalate semantic conflicts, expired authorization, missing identity sources or unexplained provider charges. Never “repair” a failure by changing owner intent, promoting an image, weakening a test, overwriting expected hashes, changing a budget or substituting a lookalike. Maintain existing usable assets while the affected replacement is blocked.

## Closeout

Report what changed, where it is saved, what was actually verified, and the one next dependent action. Use precise states: planned, prepared, submitted, generated, saved, checked, owner-approved, integrated, deployed, scheduled, published. An image prompt is not an image; a draft PR is not a deployed site; a scheduled post is not a delivery receipt.

This document is a workflow contract. The current SDK still requires the adapter/change-handler/queue implementation described in the creative audit. No self-healing daemon, cron schedule, general app completion percentage or working CRM funnel is claimed from this documentation change.
