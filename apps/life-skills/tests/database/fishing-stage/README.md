# MAIN-only native execution handoff

This directory contains authored PostgreSQL cases, **not executed evidence**. Do not run them until MAIN registers the stable candidate, both SQL hashes and the exact fresh target. The old abstract `native-contract.ts` factory has been replaced by concrete fixture/test files.

1. MAIN prepares a fresh, already-migrated PostgreSQL database using the approved existing identity registry, including optional child/minor subject constraints. Its exact name must be `ls_calendar_test_rm_stage_<32 lowercase hex>_test` (63 ASCII bytes), on `127.0.0.1`, with explicit port and process-only credentials. MAIN verifies SCRAM authentication and isolation; the fixture also checks database name, server address and `password_encryption=scram-sha-256` before any fixture DML. That setting alone is not authentication-method evidence.
2. MAIN reviews/numbers/applies the owned `src/features/fishing-stage/candidate.sql` proposal, then separately applies this directory's `fixture.sql` **only to the disposable target**. Fixture tables simulate MAIN-owned hooks; they must never enter production migrations. No fixture function performs DDL, database creation, deletion, reset or auth-constraint alteration.
3. Set process variables explicitly, without writing credentials into this repository: `TEST_DATABASE_URL`, `LS_RM_STAGE_TEST_DATABASE`, `LS_RM_STAGE_NATIVE_ALLOW=MAIN_REGISTERED_ONLY`, `LS_RM_STAGE_SCRAM_CONFIRMED=true`, `LS_RM_STAGE_SCHEMA_SHA256` and `LS_RM_STAGE_FIXTURE_SHA256`. The two hashes must match the actual file bytes being executed; preserve the registered Git/checkout newline mapping. There is no `DATABASE_URL` fallback, generic CI target, PGlite path or skipped gate.
4. From `apps/life-skills`, use the unchanged retained database config: `vitest run --config vitest.db.config.ts tests/database/fishing-stage/native-store.test.ts`. Unit tests use the unchanged retained root config once dependencies are available: `vitest run --config vitest.config.ts tests/unit/fishing-stage`.

All native tests construct the real `NativeFishingStageStore`. `fixture.ts` creates verified synthetic identity records with ordinary session/subject constraints, then uses actual PostgreSQL through Drizzle, `bindStatement` and `normalizeDatabaseRows`. It creates no clinical case, appointment, message or payment. The injected shared hooks are explicitly synthetic SQL implementations, so their capacity races and rollback assertions do not accept MAIN's actual shared capacity/resource owner.

The two concurrent tests synchronize distinct backend connections and assert distinct PostgreSQL PIDs. They are not separate-process restart tests. No process-crash/restart evidence is implemented or claimed. Fixtures close their pools; target lifecycle and cleanup remain with MAIN.

Seventeen authored native cases: persistence/reload; changed operation/selection; two-connection CAS; revoked session before hooks; selected guardian/child; actor/foreign/selection hook rejection; stale authority before commit; ordinal binding; three ciphertext domains; resource/receipt rollback; unknown occupancy/template revocation; replacement rollback/replay; actual learner-target and entitlement SQL uniqueness; two-source last-seat race; stale/full replacement.
